# M0 實驗報告：OpenAI 即時翻譯 API 的實際行為

> **日期**：2026-11-20
> **狀態**：主要實驗完成。兩組長時間實驗還在執行，結果會補在 2.4 與 2.5 節（標示「待補」）。
> **對應**：DESIGN.md 9.13 節的 M0 完成條件、12.3 節的待確認事項。

---

## 1. 結論

1. **`gpt-realtime-translate` 的中文只有簡體，而且是中國大陸用語。** API 的中文代碼只接受 `zh`；`zh-TW`、`zh-Hant` 等都被拒絕。
2. **它的英文逐字稿很好。** 產品名稱與數字全對，比聲音晚約 0.5 秒，連續 20 分鐘沒有變差。
3. **它的中文延遲大致符合設計目標。** 首字延遲中位數約 2.6–3.1 秒，句末延遲 P95 約 3.2–4.8 秒。
4. **長時間連線時，中文的格式不穩定。** 20 分鐘的測試裡，第 5.5 到 11.5 分鐘之間的中文完全沒有標點。
5. **用便宜的文字模型逐句翻譯英文，品質好很多，而且更快拿到完整的句子。** `gpt-6-luna` 平均 1.0–1.3 秒翻完一句，輸出是道地的台灣繁體中文，專有名詞保留英文；每小時約 0.03 美元。

**建議**（需要專案負責人決定，見第 3 節）：即時字幕改成兩層。英文逐字稿與「暫定」的中文來自 `gpt-realtime-translate`；每一句英文結束後，用文字模型翻成台灣繁中，取代暫定的中文。這樣錄音當下看到的就是最後存檔的品質，原本規劃的「會後重翻」只需要補漏。

## 2. 結果

### 2.0 實驗條件與限制

- **音檔**：用 macOS 的 `say` 合成，稿子在 `Benchmarks/synthetic/`，內容是為測試而寫的虛構內容。
  - `keynote`：技術主題演講，美式口音（Samantha），93 秒、19 句。
  - `lecture`：課堂講課，英式口音（Daniel），95 秒、19 句。
  - `meeting`：線上會議，印度口音（Rishi），89 秒、19 句。
  - `mixed`：中文、英文、中英夾雜，27 秒、6 句。
- **限制**：
  - 合成語音比真人演講好辨識，沒有雜訊、迴音與口吃。真實演講的結果一定比較差，還沒有測。
  - 每個設定只跑一次。延遲數字是觀察值，不是統計結論；同一段音檔兩次的結果會有差異。
  - 模型的輸出每次不同（同一段音檔兩次的中文相似度約 0.74）。
- **工具**：`Tools/thunderbench`（`translate` 以即時速度串流並錄下所有事件；`latency.py` 計算延遲；`analyze` 檢查簡繁與術語）。
- **費用**：全部實驗送出約 53 分鐘的音訊，依公告價格約 1.8 美元；若英文逐字稿另外計費，約 2.7 美元。API 不回報費用，實際金額請以用量頁為準。

### 2.1 中文輸出

- **語言代碼**：只接受 58 個兩個字母的代碼，中文只有 `zh`。`zh-TW`、`zh-Hant`、`zh-Hant-TW`、`zh-CN`、`cmn-Hant-TW` 都回傳 `invalid_value`。

  ```
  af ar az be bg bs ca cs cy da de el en es et fa fi fr gl he hi hr hu hy id is it iw ja kk kn ko
  lt lv mi mk mr ms ne nl no pl pt ro ru sk sl sr sv sw ta th tl tr uk ur vi zh
  ```

- **輸出是簡體字，用語是中國大陸的說法。** 三段音檔的譯文都沒有任何繁體專用字。例句：

  > 它提供三个核心组件:运行时、网关和内存。借助 Agent Core 运行时,每个会话都在独立的微虚拟机中运行,最长可达八小时。

- **術語**（以台灣用語為標準）：

| 音檔 | 術語 | 數字 | 沒對上的例子 |
|---|---|---|---|
| keynote | 11／19 | 8／8 | 推理（推論）、基座模型（基礎模型）、无服务器（無伺服器）、可观察性（可觀測性）；產品名稱被拆開或翻譯：Agent Core、Graviton 5、微虚拟机、S3 向量 |
| lecture | 11／11 | 4／6 | 沒對上的兩個數字（0.001、11:59）還沒確認是翻錯還是寫法不同 |
| meeting | 7／11 | 9／9 | 访问密钥（存取金鑰）、多因素认证（多重要素驗證）、集群（叢集）、行动项（待辦事項） |

- **內容偶爾會黏在一起或漏掉。** 例如把兩句合成「今天我想谈谈我们如何让建立Amazon Bedrock Agent Core——可投入生产代理变得更容易」。同一段音檔另一次執行則是正確的。
- 沒有任何方法可以給它術語表或提示（官方文件已說明，實測的設定欄位也只有三個）。

### 2.2 英文逐字稿（`gpt-realtime-whisper`，在同一條連線裡）

- **準確度**：keynote 的產品名稱與數字全對（AgentCore、microVM、Graviton5、S3 Vectors、CloudWatch、1.5 billion、30%）。偶爾的差異是空格與連字號（Agent Core、production ready）。
- **延遲**：每句的第一個字在開口後約 0.6–0.9 秒出現，最後一個字在說完後約 0.45–0.55 秒出現。
- **標點完整**，可以用來切句。
- 20 分鐘連續串流，延遲沒有變差（每 93 秒一輪，各輪的句末延遲都在 0.52–0.61 秒）。

### 2.3 延遲

以即時速度串流，每種設定一次。首字延遲：一句英文開始說，到畫面出現這一句的第一個中文字。句末延遲：一句英文說完，到下一個中文句號出現。

| 音檔與設定 | 英文句末延遲（中位／P95） | 中文首字延遲（中位／P95） | 中文句末延遲（中位／P95） |
|---|---|---|---|
| keynote，200 ms 一包 | 0.51／0.62 秒 | 2.65／4.59 秒 | 2.70／4.37 秒 |
| lecture，200 ms 一包 | 0.44／0.57 秒 | 3.11／4.83 秒 | 2.56／4.24 秒 |
| meeting，200 ms 一包 | 0.44／0.59 秒 | 2.81／3.41 秒 | 2.24／3.21 秒 |
| keynote，100 ms 一包 | 0.55／0.67 秒 | 1.83／4.26 秒 | 1.82／6.26 秒 |
| keynote，far_field 降噪、不要英文逐字稿 | — | 3.49／4.65 秒 | 3.40／4.81 秒 |

- 設計目標是首字延遲 P50 ≤ 3 秒、句末延遲 P95 ≤ 5 秒。三段音檔大致達標，lecture 的首字延遲略超過。
- 100 ms 與 200 ms 一包的差異在單次執行的誤差範圍內，無法判斷哪個比較好。
- 字幕只會往後加字，不會改寫已經送出的內容。每個事件平均 1.6 個中文字，間隔中位數約 0.2 秒。

### 2.4 長時間連線

把 keynote 循環播放 20 分鐘（12 輪），連線全程沒有中斷、沒有錯誤，正常收尾。

| 輪次（分鐘） | 英文句末延遲 | 中文字數 | 中文標點數 |
|---|---|---|---|
| 1–3（0.0–4.7） | 0.52–0.61 秒 | 526–530 | 37 |
| 4（4.7–6.2） | 0.55 秒 | 487 | 21 |
| 5–7（6.2–10.9） | 0.53–0.57 秒 | 430–441 | **0** |
| 8（10.9–12.4） | 0.56 秒 | 500 | 26 |
| 9–12（12.4–18.6） | 0.55–0.60 秒 | 514–545 | 33–48 |

- **第 5.5 到 11.5 分鐘之間，中文完全沒有標點**，數字改用國字（十五亿、百分之三十），「Amazon」變成「亚马逊」，之後自己恢復。例句：

  > 也祝大家会议愉快欢迎来到会议今天我想谈谈我们如何让构建生产就绪智能体更容易亚马逊Bedrock Agent Core提供三个核心组件运行时网关和内存有Agent Core运行时每个会话都在独立的微VM中运行

- 同一段時間，英文逐字稿的標點與內容都正常。
- 這次測試是同一段內容重複播放，不確定現象是否與重複有關。**待補**：改用三段內容輪流播放的 20 分鐘測試正在執行。
- 對設計的意義：即時中文不能只靠標點切句；存檔的中文不應該直接用這個輸出。

### 2.5 連線行為

| 項目 | 結果 |
|---|---|
| 建立連線 | 從開始連線到收到 `session.created` 約 0.87 秒；送出設定到收到 `session.updated` 約 0.1 秒 |
| 連線上限 | `session.created` 帶有 `expires_at`，是連線後 60 分鐘。可以依它精準安排換線 |
| 預先連線 | 連線並完成設定後，閒置 60 秒再開始送音訊，翻譯正常 |
| 長時間閒置與到期 | **待補**：閒置 62 分鐘的測試正在執行（目前閒置超過 20 分鐘仍然在線） |
| 比即時更快地送音訊 | 可以。以 4 倍速送出 93 秒的音訊（花 23 秒），英文與中文都完整 |
| 收尾 | 送出 `session.close` 後約 5.3 秒收到 `session.closed`，期間剩下的譯文會送完 |
| API Key 無效 | 連線會成功，接著收到 `error` 事件（`code: invalid_api_key`），然後伺服器以關閉代碼 3000 斷線。不是在連線階段回傳 401 |
| 設定被拒絕 | 回傳 `error` 事件（`code: invalid_value`，`param` 指出欄位）。**整個設定都不生效，連線停在預設值：目標語言是西班牙文、沒有英文逐字稿**。所以一定要等 `session.updated` 才能開始送音訊 |
| 預設值 | 目標語言 `es`；英文逐字稿關閉；降噪關閉 |

### 2.6 事件與時間戳

- 實際出現的事件：`session.created`、`session.updated`、`session.input_transcript.delta`（英文）、`session.output_transcript.delta`（中文）、`session.output_audio.delta`（語音）、`session.closed`、`error`。
- **沒有「一句結束」的事件**，也沒有句子或段落的編號。只有一個字一個字的增量。
- **每個事件都有 `elapsed_ms`**，是模型自己的時鐘，跟著音訊內容走，不跟著牆上的時間走（以 4 倍速送音訊時，它仍然依音訊的長度前進）。
  - 英文事件的 `elapsed_ms` 大約是那個字在音訊裡的位置（收到的時間只比它晚約 0.2 秒）。
  - 中文事件的 `elapsed_ms` 是那個字被產生的時間，不是它對應的英文位置。
  - 所以字幕的時間戳應該用 `elapsed_ms`（加上這條連線開始時的音訊位置），比用「收到的時間」準確，也不受網路延遲影響。
- 語音事件的大小是每 200 ms 約 19,200 位元組，實際是 48 kHz（事件裡寫的 24,000 與實際不符）。我們不使用語音，只影響頻寬。

### 2.7 頻寬

| 方向 | 內容 | 每小時 |
|---|---|---|
| 上行 | 24 kHz PCM16 的 base64 | 約 220 MB |
| 下行 | 用不到的譯文語音（只在有譯文時送出）＋文字 | 約 225–280 MB |

合計每小時約 450–500 MB。用手機熱點時需要提醒使用者。語音輸出沒有辦法關閉。

### 2.8 來源不是英文

`mixed` 音檔（台灣口音的中文、英文、中英夾雜）：

- 英文逐字稿會把中文也寫出來，但是簡體字。
- 中文輸出大致是把聽到的中文用簡體重述一次，夾雜的英文術語會被翻成中文（inference endpoint → 推理端点）。第一句中文被略過，只輸出「嗯,」。
- v1 只保證英文來源。中英夾雜的演講可以用，但第一句可能被略過。

### 2.9 把即時中文轉成台灣繁體

用 OpenCC 的詞表資料檔（`STPhrases`、`STCharacters`、`TWPhrases`、`TWVariants`，Apache-2.0）重現簡體轉台灣繁體的流程，套在實際的輸出上：

- **字形**：全部轉成繁體，沒有問題。
- **用語**：修正了一部分（内存→記憶體、网关→閘道器、数据→資料、用户→使用者、集群→叢集、存储→儲存、服务器→伺服器）。
- **修不到的**：推理、會話、基座模型、令牌、終端、可觀察性、護欄、訪問金鑰、多因素認證、行動項、早上好。OpenCC 的台灣用語詞表只有 858 條。
- **OpenCC 自己的詞條有些不自然**：扩展→擴充套件、实例→例項、发布→釋出。
- 結論：詞表轉換可以讓即時中文變成看得懂的繁體，但要達到台灣用語，還需要自己維護一份資訊用語表，並覆寫 OpenCC 不自然的詞條。

### 2.10 用文字模型逐句翻譯

把每一句英文（附前兩句當上下文）送給 `gpt-6-luna`（Responses API、串流、`reasoning.effort: none`），要求翻成台灣繁體中文、專有名詞保留英文。

| 音檔 | 第一個字（中位／P95） | 整句完成（中位／P95） |
|---|---|---|
| keynote | 0.83／1.14 秒 | 1.26／1.65 秒 |
| lecture | 0.64／1.01 秒 | 1.02／1.39 秒 |
| meeting | 0.65／0.77 秒 | 1.04／1.21 秒 |

- **品質**：台灣用語、標點完整、專有名詞保留英文。例句：

  > Amazon Bedrock AgentCore 提供 3 個核心元件：執行環境、閘道和記憶體。
  > 使用 AgentCore Runtime 時，每個工作階段都會在獨立隔離的 microVM 中執行，最長可達 8 小時。
  > 您可以在 3 個可用區域部署推論端點，提升處理量與韌性。
  > 請確認所有存取金鑰都已輪替，並已啟用多因素驗證。

- 小問題：序數偶爾寫成「第 2」，可以靠調整提示改善。
- **費用**：19 句（約 90 秒）用了約 5,100 個輸入 token、約 470 個輸出 token。換算每小時約 20 萬輸入、1.9 萬輸出，以 `gpt-6-luna` 的價格（輸入 0.10、輸出 0.50 美元／百萬 token）約 **0.03 美元**。
- **和即時翻譯模型比較**（完整句子出現的時間，從英文說完算起）：
  - 即時翻譯模型：中位數 2.2–2.7 秒，P95 3.2–4.8 秒。
  - 英文逐字稿（約 0.5 秒）＋文字模型（約 1.0–1.3 秒）：約 1.5–1.8 秒。
  - 即時翻譯模型的優勢是句子還沒說完就開始出字（首字延遲約 2.6–3.1 秒）；文字模型要等整句英文結束。
- 這個量測是「把句子一句一句送出」，還沒有接上真正的即時英文串流。切句的邏輯與實際的端到端延遲要在 M2 驗證。

## 3. 對設計的影響

### 3.1 需要專案負責人決定：即時字幕改成兩層

| | 現行設計 | 建議 |
|---|---|---|
| 當場看到的中文 | 即時翻譯模型的輸出，經詞表轉成繁體 | 先顯示即時翻譯模型的輸出（轉成繁體，標示為暫定）；每句英文結束後約 1.5–1.8 秒，換成文字模型翻的台灣繁中 |
| 存檔的中文 | 結束後整場重翻 | 就是當場的定稿；結束後只補沒翻到的句子 |
| 術語與台灣用語 | 當場做不到，存檔才有 | 當場就有 |
| 格式不穩定（2.4 節） | 會直接出現在畫面上 | 只影響暫定的那一層 |
| 額外費用 | 會後重翻，每小時約 0.01–0.03 美元 | 每小時約 0.03 美元（取代會後重翻） |
| 代價 | — | 多一個「依英文標點切句」的元件；畫面上暫定的文字會被替換一次 |

另一個可以之後再評估的方向：不用即時翻譯模型，只用純轉錄的連線（`gpt-live-transcribe`，可以給關鍵詞，每分鐘 0.017 美元）加上文字模型。費用大約是現在的一半，但句子說完之前畫面上不會有中文，而且要由用戶端自己決定何時送出一段音訊。這個方向還沒有實測。

### 3.2 不論是否採用 3.1 都要改的

1. **引擎要等 `session.updated` 才開始送音訊**；設定被拒絕要當成無法繼續的錯誤，否則會得到西班牙文。
2. **字幕的時間戳改用 `elapsed_ms`**（加上這條連線開始時的音訊位置）。
3. **換線依 `expires_at` 安排**，不必猜測上限。
4. **API Key 無效是以事件加上關閉代碼 3000 回報**，不是 HTTP 401。
5. **即時中文不能只靠標點切句或分段**；沒有標點時要依停頓與長度切。
6. **即時中文一定要轉成繁體**：OpenCC 的詞表資料加上自己維護的用語表（2.9 節）。
7. **按下開始之前可以先連線**，省下約 1 秒。
8. **文字模型用 `gpt-6-luna`**（重翻與逐句翻譯）。`gpt-5-nano`、`gpt-5-mini` 將在 2026-12-11 停用，`gpt-4.1`、`gpt-4o` 系列在 2027-01-14 停用。
9. **benchmark 可以用 4 倍速送音訊**，節省時間（延遲的量測仍然要用即時速度）。

## 4. 還沒回答的問題

- **真人演講的表現。** 需要真實的錄音，包含現場收音與口音。這是下一步最重要的驗證。
- **長時間閒置與 60 分鐘到期時的行為**（待補）。
- **標點消失是否與重複的內容有關**（待補）。
- **英文逐字稿是否另外計費。** 只能從 OpenAI 的用量頁確認。
- **純轉錄連線加文字模型**的延遲與品質（3.1 節的另一個方向）。
- **逐句翻譯接上即時英文串流後的端到端延遲**，以及句子很長時的處理方式。

## 5. 重現方式

```sh
cd Tools/thunderbench && swift build -c release
B=../../Benchmarks
```
