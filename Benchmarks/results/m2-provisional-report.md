# M2 實驗報告：整句的暫定譯文（2026-11-22）

## 結論

1. **暫定譯文要開著。** 負責人實際使用後認為開著好得多，因為中文早出現。但原本的暫定譯文是逐段翻的（D32 之前就是這樣），有兩個問題：
   - 灰字每句平均被改寫 1.2 次。
   - 各段硬接起來的半句不通順。
2. **改成整句的暫定譯文（D33）。** 做法：
   - 翻「這一句目前聽到的部分」。
   - 請求帶上畫面上已經有的暫定譯文，請模型盡量保留，翻錯或接不通順才改。
   - 每一句的第一個請求 2 個字就送。

   正式引擎的結果如下：

   | | 改之前 | 改之後 |
   |---|---|---|
   | 第一個中文字 | 1.06 秒 | **0.71 秒** |
   | 灰字之間每句改寫 | 1.2 次 | **0.6 次** |
   | 灰字之間被擦掉的字 | 33% | **8%** |
   | 白字（一句說完後出現） | 約 0.9 秒 | 約 0.9 秒（不變） |

   暫定譯文本身也從各段硬接的半句，變成一整句通順的中文。
3. **其他試過、沒有採用的做法。**
   - 「一字不改地保留」最穩，每句只改 0.1 次，但翻錯的開頭會一路留著。
   - 「照英文的語序翻」偶爾跟不上講者。
   - 「整句定稿也保留暫定譯文」換白字時改得少，但會把暫定譯文的怪詞帶進定稿。
   - 「只顯示連續兩版相同的開頭」幾乎不擦字，但每個字晚 1.5 秒以上。
4. **正式引擎抓到一個模擬沒抓到的問題。**
   - 上一句的整句定稿還沒回來時，前文只有英文。模型會把那一句也翻進這一句的暫定譯文，「保留」的規則又讓它留到這一句結束。修正之前，39% 的句子受影響。
   - 修正：前文只帶已經翻好的句子，也不採用出現原文沒有的英文字的版本。
   - 修正後，換白字時大改的句子剩 14%。這些都是白字把囉嗦的直譯濃縮成精簡的句子，屬於正常。
5. **白字的提示加上「不要加入原文沒有的資訊」。** 盲測：99 句白字不同的句子裡，`gpt-6.1-terra` 當裁判、A/B 順序隨機，加規則的版本勝 53 句，原本的勝 26 句，20 句差不多。出現的時間不變。
6. **白字（整句定稿）不換模型。** 用 `gpt-6.1-terra` 只略好，但每句晚 0.38 秒，費用約 10 倍。
7. **「加速翻譯」（OpenAI 的 Fast mode，`service_tier: priority`）做成設定、預設關閉，待負責人決定。** 正式引擎（同一段音檔、其他設定相同）：第一個中文字 0.72 → 0.60 秒，白字 0.93 → 0.77 秒（英文確定後的 P95 1.66 → 1.23 秒），改寫的次數不變；翻譯的單價約 2 倍（每小時多約 0.27 美元，總費用約多兩成）。 每個請求快約 0.14 秒，但單價較高。

## 1. 條件

- **材料**：和 `m2-sentence-report.md` 相同，37C3「NEW IMPORTANT INSTRUCTIONS」（CC BY 4.0）第 3–13 分鐘，共 600 秒。音檔與逐字稿不進 repo。
- **基準**：`thunderbench live --sentences`，也就是 D32 的整句定稿加上逐段的暫定譯文。共 129 句。
- **模擬**：`Tools/thunderbench/provisional-sim.py`。
  - 用基準錄下的英文時間軸，在虛擬時間裡重播各種做法。
  - 請求真的送到 `gpt-6-luna`（reasoning none）。回來的時間＝送出的時間＋實測的請求時間，串流的每一塊都照實際時間顯示。
  - 模擬「D32 的做法」，和正式引擎幾乎一樣：第一個中文字 1.07 秒對 1.06 秒，被擦掉的字都是 91%。
- **指標**（每一句）：
  - **第一個中文字**：這一句第一個英文字出現後，第一個中文字出現的時間。
  - **每個字的延遲**：每個英文字出現，到涵蓋它的中文出現。
  - **被擦掉的字**：畫面上已經顯示、後來被換掉的字數，除以白字的字數。分成「灰字之間」與「換成白字那一次」。
  - **灰字之間每句改寫**：灰字更新時，改到已經顯示的字的次數。
  - **白字**：一句說完到整句定稿出現的時間。

其他兩項：
- 白字換成 `gpt-6.1-terra`：白字 0.86 → 1.24 秒；129 句花 0.079 美元（`gpt-6-luna` 約 0.01）；品質只略好。
- `service_tier: priority`（24 個請求各一次）：第一個字 0.58 → 0.44 秒，完成 0.90 → 0.76 秒。
- 轉錄延遲 `minimal`（正式引擎，和 `low` 比）：同一個英文字早 0.24 秒出現（對到 1,673 個字的中位數），中文也跟著早；和官方字幕（機器產生，本身有錯）比，字錯率 8.4% → 8.9%；句子 125 → 137，切得比較碎。預設維持 `low`，設定頁可以切換。

## 3. 正式引擎

用 `thunderbench live --sentences --sentence-provisional --provisional-first-words 2` 跑同一段音檔，設定和 App 相同。

| | D32（基準） | D33，修正前 | D33，修正後 | 加上白字的新規則 |
|---|---|---|---|---|
| 句 | 129 | 114（跑到一半） | 125 | 125 |
| 第一個中文字（中位數／P90） | 1.06／1.78 秒 | 0.66／1.25 秒 | **0.71／1.24 秒** | 0.72／1.26 秒 |
| 被擦掉的字：灰字之間／換白字 | 33%／58% | 10%／115% | **8%／73%** | 8%／71% |
| 灰字之間每句改寫 | 1.2 次 | 0.6 次 | **0.6 次** | 0.7 次 |
| 換白字時被擦掉超過白字 1.2 倍的句子 | 8% | 39% | 14% | 9% |
| 白字（一句說完後，中位數／P90） | 0.90／1.93 秒 | 0.87／1.91 秒 | 0.97／1.90 秒 | 0.93／1.77 秒 |

- **修正前**：39% 的句子在換白字時大改，原因是前文裡只有英文的上一句被翻進暫定譯文。
- **修正後**：大改的句子剩 14%。看過每一句，都是白字把囉嗦的直譯（重複、改口、口頭禪）濃縮成精簡的句子。
- **App 本身**：開視窗跑 2 分鐘，主執行緒最長卡頓 32 ms（預算 100 ms）。

```sh

export OPENAI_API_KEY="$(security find-generic-password -a "$USER" -s thunderflow-openai-dev -w)"
$B/.build/release/thunderbench live clip.wav --sentences --events run3/events.jsonl
$B/.build/release/thunderbench live clip.wav --sentences --sentence-provisional --provisional-first-words 2 --events run5/events.jsonl
# 模擬：快取與結果寫到 SIM_WORK（不要放進 repo）；每一種做法約 0.03 美元，重跑用快取不花錢
export SIM_WORK=/tmp/sim
python3 $B/provisional-sim.py real run3/events.jsonl --tag 3
python3 $B/provisional-sim.py run run3/events.jsonl p0 --stream 1 --tag 3st
python3 $B/provisional-sim.py run run3/events.jsonl s2r --stream 1 --first-words 2 --tag 3first2
python3 $B/provisional-sim.py post $SIM_WORK/out/p03st.json mask2 la2 hold6
```
