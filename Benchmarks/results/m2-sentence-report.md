# M2 實驗報告：一句說完就整句重翻（2026-11-22）

## 結論

1. **逐段翻譯讓中文零碎。** 真人演講一停頓就切段，124 句裡有 42 句（34%）被切成 2 段以上，各段各自翻譯：接起來會重複或斷掉，半句的段甚至會亂翻（187 段裡 2 段出現和原文無關的詞）。
2. **一句說完就整句重翻，中文明顯通順，而且一樣快。** 附上前三句的英文與已經翻好的中文、要求去掉口語贅字，用同一個模型（`gpt-6-luna`、reasoning none）：整句定稿在一句說完後中位數 0.93 秒、P95 1.20 秒出現，和段的定稿（0.88／1.44 秒）差不多。整場一次翻（DeepSRT 的做法）一樣通順、術語更一致，適合會後精修。差距在做法，不在模型。
3. **「字一直變」主要來自暫定譯文。** 保留暫定譯文時，不論逐段或整句，約 85% 的句子在畫面上被改寫過；關掉暫定譯文、只讓淡色的各段定稿換成整句定稿一次，降到 34%，代價是第一個中文字從這一句開始後 1.1 秒晚到 3.6 秒（英文照樣邊講邊出）。
4. **決定（D32）**：App 改用整句模式，暫定譯文預設關閉，字幕不顯示句尾的「。」。翻譯費用每小時約 0.08 美元（原本含暫定譯文約 0.12）。

## 1. 條件

- **材料**：37C3「NEW IMPORTANT INSTRUCTIONS」（Johann Rehberger，CC BY 4.0，media.ccc.de）第 3–13 分鐘，共 600 秒。現場演講、單一講者、英文流利、口語（常用 right、you know、kind of）。音檔與逐字稿不進 repo，報告只列統計數字。
- **即時引擎**：`thunderbench live`，設定和當時的 App 相同（`gpt-live-transcribe`、delay low、暫定譯文開啟），`--events` 把每個事件與時間寫下來。
- **三種中文**：用同一份英文（即時引擎聽到的英文），同一個模型與設定，差別只在怎麼翻：
  1. **現在**：逐段翻。直接用即時引擎當場的段定稿。
  2. **A**：一句說完就整句重翻。依序呼叫，每句附前三句的英文與 A 自己的中文（模擬當場只看得到前文）。
  3. **整場一次翻**：整場的句子編號後一次送出，結構化輸出，每句一個編號（DeepSRT 的做法）。
- **句子**：把連續的段合到以句尾標點結束為止（一句最多 60 個字）。
- **畫面上的改動**：用即時引擎事件的時間，重建每一刻畫面上顯示的中文；A 的整句定稿在一句說完後，加上實測的請求時間出現。被換掉的字＝已經顯示、之後被換掉的字；有改寫的句子＝至少一次換掉已經顯示的字。

## 2. 結果

### 2.1 切段

| | 數字 |
|---|---|
| 段 | 187（每段中位數 8 個字；這位講者停頓多，M0b 的錄音是 13 個字） |
| 句 | 124 |
| 被切成 2 段以上的句 | 42（34%） |
| 英文只有 1–2 個字的段 | 9 |

### 2.2 中文的品質（人工逐句看過）

- **現在**：一句被切開時，各段各自成句（例如三段各自翻成完整的句子、主詞重複），接起來不通順；常見兩段之間重複同一個詞，或停在「……」。2 段出現和原文無關的詞（都是半句的段：一段只有一個字，一段停在形容詞）。
- **A**：通順，依中文的語序重組，去掉了口頭禪；沒有漏翻（沒有中文字數比英文字數明顯少的句子），沒有留下整串英文。
- **整場一次翻**：和 A 一樣通順，前後的用語更一致（例如同一個術語全場同一個譯法）。

### 2.3 速度與費用

| | 中位數 | P95 |
|---|---|---|
| 段的定稿（一段的英文確定之後） | 0.88 秒 | 1.44 秒 |
| A 的整句定稿（一句說完之後，含請求） | 0.93 秒 | 1.20 秒 |
| 整場一次翻（124 句一次） | 27 秒 | — |

A 的請求：10 分鐘約 6.3 萬個輸入 token、0.3 萬個輸出 token，換算每小時約 0.05 美元。

### 2.4 畫面上的改動

| 顯示方式 | 被換掉的字 | 有改寫的句子 | 第一個中文字（這一句的第一個英文字出現後，中位數） | 白字到齊（說完後，中位數／P95） |
|---|---|---|---|---|
| 現在（暫定譯文 → 段的定稿） | 38% | 86% | 1.1 秒 | 0.9／1.4 秒 |
| 現在，關掉暫定譯文 | 2% | 6% | 3.7 秒 | 0.9／1.4 秒 |
| A（段先出，整句定稿取代） | 52% | 85% | 1.1 秒 | 0.9／1.2 秒 |
| **A，關掉暫定譯文** | 24% | **34%** | 3.6 秒 | 0.9／1.2 秒 |
| A，只顯示暫定譯文連續兩版相同的開頭 | 30% | 47% | 2.7 秒 | 0.9／1.2 秒 |

- A 的「白字」（整句定稿）之後不再改變；畫面上的改寫都發生在淡色的字。
- 「A，關掉暫定譯文」時，只有被切成好幾段的句子會改一次：淡色的各段定稿換成整句定稿。

## 3. 正式引擎的驗證

實作之後（D32），用 `thunderbench live --sentences --no-provisional` 對同一段音檔跑一次正式的引擎（和 App 的新預設相同）：

| | 實驗的模擬（A，關掉暫定譯文） | 正式引擎 |
|---|---|---|
| 段／句／切成 2 段以上的句 | 187／124／42（34%） | 185／124／44（35%） |
| 整句定稿（一句說完之後） | 中位數 0.93 秒，P95 1.20 秒 | 中位數 0.93 秒，P95 2.06 秒 |
| 第一個中文字（這一句的第一個英文字出現後） | 中位數 3.6 秒 | 中位數 3.5 秒，P95 7.4 秒 |
| 畫面上被改寫過的句子 | 34% | 42%（每句最多一次） |
| 用到備用譯文（各段的定稿接起來）的句子 | — | 0 |
| 含簡體字的定稿 | — | 0 |

- 124 句全部有整句定稿。112 句以「。」結尾，畫面上會拿掉。
- 被改寫的 52 句裡，44 句是被切成好幾段的句子（照設計會換一次）；另外 8 句只有一段，因為句子在這一段確定之後才結束（2.5 秒沒有新的字，或晚到的句號），這一段自己的定稿已經先用淡色顯示，再被整句定稿換掉。模擬時假設句號在一段確定的當下就知道，所以少算了這 8 句。這 8 句也可以改成直接沿用段的定稿（畫面不變，但不會去掉口語的贅字）。
- 平均每句被改寫的次數：現在 2.0 次，整句模式 0.42 次。

## 4. 重現方式

```sh
B=Tools/thunderbench
# 下載材料（media.ccc.de 的 mp3，CC BY），轉成 24 kHz 單聲道，取第 3–13 分鐘
afconvert -f WAVE -d LEI16@24000 -c 1 talk.mp3 full.wav
# 即時引擎（會產生 API 費用，10 分鐘約 0.17 美元）；Key 只從 Keychain 讀進環境變數
OPENAI_API_KEY="$(security find-generic-password -a "$USER" -s thunderflow-openai-dev -w)" \
  $B/.build/release/thunderbench live clip.wav --events run/events.jsonl > run/live.log
# 三種中文與畫面上的改動（約 0.01 美元）
OPENAI_API_KEY=... python3 $B/sentence-retranslate.py run/events.jsonl exp
python3 $B/sentence-report.py exp/result.json exp/report.html
# 正式引擎的整句模式
OPENAI_API_KEY=... $B/.build/release/thunderbench live clip.wav --sentences --no-provisional --events run2/events.jsonl
python3 $B/sentence-validate.py run2/events.jsonl
```
